# MeFit account linking and rollback

The Supabase API resolves a linked issuer and subject to the original MeFit user. The link lives in a separate table with one link per MeFit account, a unique issuer and subject pair, and row-level security with no client policies. Account linking and linked sign-in leave the existing sign-in ID, account fields, role assignments, and fitness data intact.

The linking endpoint requires an MFA-verified Supabase bearer token and a current Keycloak access token for the configured MeFit audience. It looks up the legacy account by the signed Keycloak subject and verifies the user's confirmed email with the configured Supabase Auth project. The confirmed email must match the existing account. The endpoint accepts retries for the same pair and rejects attempts to replace a link. Normal setup returns `ACCOUNT_LINK_REQUIRED` for an existing email until the user links their sign-ins. New users can continue through normal setup.

## Before a production rollout

1. Review the [additive SQL migration](../../apps/api/prisma/migrations/20261122150000_add_supabase_identity_links/migration.sql) and obtain approval before applying it to production. It creates the link table, uniqueness constraints, a foreign key, and row-level security. There is no backfill. Apply only this reviewed migration after checking the production migration history.
2. Test against a separate API deployment and protected frontend with dedicated accounts. Provide an account-linking screen that takes users through the existing Keycloak sign-in and sends its access token from memory to `POST /api/user/link`. Keep both tokens out of URLs and logs. Test the full path through MFA and each provider, including registration, email verification, login, and profile creation, retrieval, and update.
3. Confirm a dedicated existing account retrieves the same profile through the current production API before and after linking. Confirm the old API's actual database target and compare it with the new API's target. The legacy Blueprint references Render Postgres, while the new Blueprint targets Supabase. If they are separate, agree on how to reconcile profile updates since the database copy and how to protect writes and new registrations made during a rollback window. Preserving IDs alone cannot synchronize two databases.
4. Keep Vercel deployment `dpl_GLV2sU7CcCmnX4GZJivvqUZuq2cq` and the current Keycloak and legacy API services available. If rollback is needed after a separately approved cutover, restore that deployment and verify legacy profile access. Keep the additive link table in place during rollback.
